- **B38 — brute-force throttle on the password-login surfaces** ✅ DONE (2026-06-01, follow-up to B35). Both password-login surfaces — the open `POST /api/launcher/login` (desktop tunnel-setup, B35) and the web `/login` form action — accepted unlimited email+password guesses. Added a **shared** throttle used by both so behavior is identical. **(a) `src/lib/server/loginThrottle.ts`** — counts failures independently per **client IP** and per **target email**; a lockout on EITHER scope blocks the request. Policy is **asymmetric** by design: **IP** = 10 free attempts, then exponential backoff (1 min doubling, capped at **1 h**), 1 h decay; **email** = 5 free attempts, backoff (30 s doubling) capped at **15 min**, 30 min decay. The short email cap deliberately bounds the **account-lockout DoS** (a remote attacker who knows an email — possibly the owner's — but not the password could otherwise freeze that login): worst case is a brief, self-healing delay, not a sustained denial. Residual accepted risk: repeated short delays on a known email can't be fully eliminated without CAPTCHA/PoW (out of scope). A scope decays to zero when quiet; a successful login clears both. `checkLoginThrottle()` runs BEFORE the scrypt verify (returns `{blocked, retryAfterSeconds}`); `recordLoginFailure()` after a bad verify; `recordLoginSuccess()` after a good one. Every DB call **fails open** (logs + allows) so a DB hiccup can't lock the whole team out. **(b) Storage = Postgres `login_attempts` table** (`key` PK = `ip:<addr>`|`email:<addr>`, `failures`, `locked_until`, `updated_at`) via Drizzle — migration `drizzle/0006_blushing_snowbird.sql`. Chosen over an in-memory map because the launcher restarts on every Railway deploy and may scale horizontally (in-memory would silently reset/shard the counter). Tradeoffs (both acceptable at this scale): a read-modify-write under high concurrency can lose an increment (only ever *under*-counts, never over-locks); and rows are deleted only on success, so never-succeeding scanner IPs accumulate slowly — the decay logic ignores their stale counts, so it's housekeeping, not correctness (prune rows older than the decay window if the table grows). **(c) Both endpoints** now take `getClientAddress()` and reject with **429** + generic message (`Retry-After` header on the JSON endpoint). ### Key lessons
Full list (+ the 2026-05-29 session lessons) in `docs/history.md#key-lessons`. The operationally-critical few:
- **Always `git push`** after committing — Railway can't deploy local-only commits.
- **Railway staged vars** — adding a var only stages it; click "Apply changes / Deploy". Prefer a **code default** for non-secret config so deploys don't depend on the dashboard.
- **Cloudflare blocks `Python-urllib` UA with 403** — always send a custom User-Agent to ComfyUI.
- **Windows trailing-dot folders** — Windows silently strips a trailing `.` (`symbols.` → `symbols` locally but NOT on Linux/R2); normalize path segments in R2 manifests. Watch on any Windows-sourced data.
- **The desktop `Invisible_Launcher.py` runs from source under Python 3.9** (VS `Python39_64`) — so **no PEP 604 `X | None`** or other 3.10+ runtime syntax in annotations (the built exe uses a newer Python and hides it). The file now carries `from __future__ import annotations` (lazy annotations) to neutralize this; keep it.
