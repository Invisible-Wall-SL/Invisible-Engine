## Recent changes
- 2026-07-16 — **Validation catches loop-scope authoring bugs at authoring time** (two live crashes on `bookofborutremake` that only surfaced at runtime). Both had the same root: the validator mapped bare `derivePins(node, ctx)` over the graph, so it saw neither the loop a node sits in nor what an incoming data EDGE carries. New `packages/engine-flow-v2/src/scope.ts` — `deriveGraphPins(graph, ctx)` resolves both (an exec walk from each `forEach`'s `body` pin gives each node its enclosing loop; the loop's element type comes from whatever feeds its `in`, edge-first, matching the runtime's `resolveDataIn` precedence) and threads them into `derivePins` as the new `PinScope` (`{ item, wiredIns }`). Consequences: (1) a `forEach.item` fed by wire (`gameSignals.winInfo.wins → forEach.in`, the normal way) is now TYPED, so wiring it into a typed pin (`item` (a `Win`) → `showWinLine.positions` (`list<Position>`) → `o.map is not a function`) reports `type-mismatch` AND is rejected by the connect gate — `/flow-v2` now derives its canvas pins, inspector pins and drag gate from the same `deriveGraphPins` the panel uses, so the drop gate and the panel can't disagree; (2) `$item.<member>` is checked against the scope struct, so a typo (`$item.pisition` on a `Win` → `undefined is not iterable` → the awaited action never resolves → the round hangs forever) reports `accessor-unresolved` naming the struct + its valid fields; an accessor that resolves is also type-checked against its pin. New `data-in-shadowed` warning code (+ panel glyph) for a data-in fed by BOTH an edge and a stored literal/accessor — the edge silently wins at runtime, which is what made bug 1 read as "my accessor is ignored". **Never guess** is the governing rule: every scope-dependent check fires only where the scope actually resolved (`$trigger`/`$input`/orphan-chain scopes stay accepted structurally), so nothing valid is flagged — verified headlessly against the user's real saved doc (the `pisition` typo fires; nothing else new) and against `LINES_FLOW_V2_DOC`, `SAMPLE_DOC` + `StaggerStop` (0 issues before AND after). Cyclic/self-feeding graphs are bounded (loop stack keyed walk + recursion guards), resolving to "unknown" rather than hanging.
- 2026-07-16 — **Fullscreen — BUILT (the SDK never had it).** Stake shipped the `jurisdiction.disabledFullscreen` permission flag but no mechanic: on Stake the casino wrapper owned the button, so the game only needed to know if it was allowed. (`OnPressFullScreen` in `components-layout` is unrelated — a canvas-sized transparent press target.) Now: `stateFullscreen.svelte.ts` in `state-shared` (toggle + `isFullscreenSupported` + an `active` flag driven ONLY by `fullscreenchange`, since Esc exits without touching the button), `fullscreen` in `ENGINE_ACTION_CATALOG` (→ projects an `onFullscreen` pin), `toggleFullscreen` book-of vocab command + `INTENT_COMMANDS` → the `fullscreen` intent, and the `Game.svelte` handler (`active` = real browser state; `disabled` when unsupported or `disabledFullscreen` — the first consumer of that jurisdiction block). **Authoring rule: wire `onFullscreen` DIRECTLY to `toggleFullscreen`** — browsers reject `requestFullscreen` outside a user gesture, and a `delay` (or any awaiting node) ahead of it spends the gesture. That the interpreter reaches `env.effect` synchronously from the press is load-bearing but invisible in the source, so it's pinned by `tools/flow-spike/flowV2Fullscreen.ts` (`pnpm --filter flow-spike run v2fullscreen`, 6/6, incl. a delay CONTROL proving the test can fail). ⏳ **Real fullscreen entry is UNVERIFIED** — the Browser pane blocks it by Permissions-Policy (`TypeError: Permissions check failed`); needs a real-browser check on an authored button, and the iframe `allow="fullscreen"` guard is spec-correct but untested (the pane reports `fullscreenEnabled: true` regardless).
- 2026-07-16 — `menuClose` HUD action, so an authored submenu can CLOSE itself. A submenu was already authorable with no engine change (any Scene-Editor screen auto-syncs into `doc.containers`, so `<menuButton>.onMenu → showContainer(Submenu)` works and suppresses the coded `stateUi.menuOpen` drawer), but the submenu's close button had no catalog action to bind → no pin → nothing to wire into `hideContainer`. Added `menuClose` to `ENGINE_ACTION_CATALOG` + label "submenu close" (`componentCatalog.ts`) and registered its handler in `Game.svelte` (`doCloseMenu`, routed via `routeActionThroughFlow` + an `invokeHostIntent` arm), so it projects an `onMenuClose` pin like every other action. Unwired it closes the coded drawer (parity). The editor's `action` dropdown renders from the LIVE catalog, so it appears on existing pinned button defs without a re-save.

- 2026-07-15 — `onTapToStart` fires from the TAP (refined). Initial "Option B" fired `tapToStart` from `dispatchFlowV2Complete` (only when a tap RESOLVED a screen complete — a held container / `complete:<id>`), so a flow that drives the start purely off the Game Signals `onTapToStart` pin (loading screen NOT held) never fired it, and the tap did nothing.
