# Invisible Game Maker — status

> Design: [docs/design/invisible-game-maker.md](../design/invisible-game-maker.md) · Guide: [docs/tools/game-maker.md](../tools/game-maker.md) · Agent: none yet (launcher tool — closest owner `.claude/agents/launcher-studio.md` + `.claude/agents/engine-pixi-svelte.md`)

**One-line state:** shipped — create a project, then one-click **Publish** freezes an immutable published snapshot players boot (Make live = rollback, Republish all = bulk) on one shared engine runtime; no repo, no build. Math/config comes from [Game Config](game-config.md); behavior tracks (Phase 4) are unbuilt.

## Current state

Closes the "author online → play" gap without a per-game repo, CLI, or desktop build. Ships **one prebuilt generic engine runtime** that boots any project from R2 — players from the project's **published snapshot**, authors (launcher links, `ie_authoring=1`) from its live authoring data. Publish is a **data + manifest operation, not a build**.

- **Scaffold** — the `gameMaker` tool at `/game-maker` (full-page; `admin`, `developer`, `pipelineTester` by default). "Create a game" seeds the launcher project + its cloud scaffold (`editor/scenes.json`, `atlas_config.json`, `manifests/`, `input/refs/`, `sheet_config.json`, `localization/strings.json`) — same scaffold as the `/admin` create action. Any tool holder can create; you then author with the existing online tools (editor / atlas / sheet / fonts / symbols / localization).
- **Publish** (Phase 1, `/api/game-maker/publish`, `gamePublish` capability) — assembles the runtime bundle ONCE, re-checks the flow it actually ships, and freezes bundle + a copy of `deploy/` as an immutable **published snapshot** (`publishedRuntime.ts`; R2 `<client>/<project>/published/`), then mints/reuses a per-project **read-only token** for the runtime's public live fetches (never exposes the shared deploy token), read-modify-writes `test_server/games.json` with `{ protocol, name, runtime }`, upserts the portal `games` row with a runtime-pointed launch URL, best-effort refreshes the test server, and only then points players at the new snapshot. Result plays at `https://games.invisiblewall.org/<key>/` against the mock RGS. **Refusals** (409, before anything is written): draft sounds (any publisher may override), flow validation errors (#833) and paytable drift against a stored partner reference (#855) — those two only the admin role may override, and bulk skips them; a desktop-built game is final. Non-blocking post-publish notes: sound licences, a missing flow, and spine bundles that resolved to nothing (#839).
- **Published snapshots + rollback** (2026-09-29) — player boots (`/api/editor/runtime` without `authoring=1`) read the pointer's snapshot: no exporters, two cached R2 reads, `ETag` = snapshot id (reload → 304), `assetBase` = `/api/published/f/<token>/<project>/<id>/` served `immutable`. Five snapshots retained; the Game Maker card shows the live one and **Published versions → Make live** flips the pointer (`POST /api/game-maker/rollback`; reviving a flow-override version is owner-only). **Play ↗** opens the published version, **Live ↗** the current authoring data. A game published before snapshots falls back to the live assemble (logged `no published snapshot`) until republished. Design + the full-copy-vs-hashed-names decision: [live-assets.md § Published snapshots](../design/live-assets.md).
- **Publish pins the session** — after a successful publish the endpoint `setActiveProjectKey(session, project)` so the top bar + home selector land on the just-built project (fixed the "selection jumps to another client on Re-publish" footgun).
- **Generic runtime (Phase 0)** — `GET /api/editor/runtime?project=&k=` (`runtimeBundle.ts`) serves a project's full `BakedBundle` live; `apps/lines` boots it via opt-in `?runtime=1`, parity-guaranteed byte-identical when off. Assets served via the **path-form** `/api/deploy/f/<token>/<client>/<project>/<...rel>` route so Spine/spritesheet/bitmap-font sub-pages resolve relative to their parent URL.
- **The live (authoring) assemble is single-flighted + briefly cached** (`runtimeBundleCache.ts`). A game-side retry (`fetchRuntimeWithRetry`) JOINS the in-flight assemble rather than starting another cold one; the two only work as a pair. Publish and a `/config` save invalidate it; TTL rules are in open item 4.
- **A stale fallback is now visible to AUTHORS** — `?ie_authoring=1` (added only by the launcher's own launch links, never by the published/copied URL) shows a red banner when the game falls back to baked data. `window.__IE_RUNTIME_STALE__` is set for every boot regardless.
- **Stale-ENGINE badge on each project row** (2026-07-27) — a game runs the SHARED runtime bundle (`_runtime/lines`), so an engine change reaches it only via a Runtime release; nothing in the UI signalled that the running game predated the current engine (the "my fix isn't showing" ghost-chase). The loader now compares the runtime bundle's release time — `headObject('test_server/_runtime/<id>/index.html').lastModified`, an existing R2 signal, no new stamp — against the game's own last publish (the manifest entry's `updatedAt`). When the runtime shipped AFTER the game's last publish it shows an amber **"Engine update available"** badge with a **Republish + Reconcile** button that runs the existing publish flow (re-export + cache invalidate + POST test-server `/refresh` = the reconcile) and, for admins, a "still stale? purge edge cache" link to `/admin`. Comparison is conservative: missing `runtime`/`updatedAt` or an absent bundle ⇒ not comparable ⇒ no badge (no false alarm); a comparable-and-current game shows a subtle "engine up to date". Read-only — it changes nothing about how games run. Helper: `runtimeBundleReleasedAt` in `testServerManifest.ts`.

- **Bulk republish — one button for a whole engine release** (2026-08-24). The stale badge told you a game was behind the shipped runtime, but clearing it was a per-project chore: open every project, press *Republish + Reconcile*. The hub header now carries **Republish N stale games** (shown only while something is stale) and **Republish all (N)**, gated on `gamePublish` like Publish itself, running the SAME `publishGame` flow per game — no second publish path to keep in sync. Shape: an in-memory job (`publishAllJob.ts`) walking targets **sequentially** in the BACKGROUND (`publishAllRunner.ts`), polled by the page at `/api/game-maker/publish-all` (GET status · POST start · DELETE stop).
  - **Background, not a long request** — a publish re-runs all seven exporters (~17-19s each measured), so a 20-game run outlives any request timeout and would pin the author's tab open. The job survives navigation; re-opening the page re-attaches to the run.
  - **Sequential, not fan-out** — the exporters are the launcher's most memory-hungry path (a parallel bake has OOM'd the service), and parallel publishes would also make the CAS retries on the shared `test_server/games.json` fight each other. The per-project Publish buttons are disabled while a run is in flight for the same reason.
  - **A blocked publish is `skipped`, not a failure** — a desktop-built game in the list is an expected outcome in bulk (`PublishBlockedError` → skipped with its reason), and a genuine failure is reported in place while the run continues. One bad project can't strand the rest.
  - **Cancel stops BETWEEN games** — the in-flight publish always finishes, because a publish is a multi-step R2 + manifest write and aborting mid-way half-registers a game.
  - **It deliberately does NOT pin the session's active project.** The single-project endpoint does (publishing one game is a statement about which game you mean); doing it for a bulk run would move the selection to whichever game happened to be last.
  - **One definition of "stale", shared** — the badge's comparison moved into `engineStaleness.ts` (`engineStalenessIndex`), used by both the page loader and the bulk endpoint, so the button's count and the run's target list can never disagree.
  - The job lives in process memory: a launcher restart mid-run loses the progress view but not the work (each publish is atomic); re-running is the recovery, and it is idempotent.

- **The project hub is now a browsable catalogue, not a list** (2026-08-20). Three changes to the `/game-maker` "Your projects" card:
  - **Per-project profile chips** replace the old row of tool-launch buttons (Edit/Atlas/Fonts/Symbols/Localization — they duplicated the tool top bar and said nothing about the game). A **Game** row states the identity (kind · win model · board · paylines · RTP · max win · runtime bundle · mock-RGS protocol · own-config-vs-template) and a **Using** row lists the optional mechanics actually switched on (wild/scatter/multiplier symbols, cascade, multiplier collect, expanding book, buy feature, ante, stacked pictures, win line + full-payline trace, per-line colours, win replay + dim/hold, highlight, board glow, book VFX, anticipation, explosion states, named symbols, big-win tiers, escalation). Built by `src/lib/server/gameProfile.ts`, which is **a data table of detectors over one `ProfileContext`** — a new mechanic is one entry there, no page/loader edit — deliberately so a shipped optional feature can't stay invisible on the hub. Costs **two extra R2 reads per project** (the Game Config + the Symbols doc); everything else was already loaded. One trap encoded: the special-property gate is "on the strips **OR** has a paytable", not `symbolsInPlay` alone — the reference `lines` wild `W` is dictionary+paytable and never on a *cosmetic* padding strip, so the strips-only gate reported "no wild" for a game that plainly has one.
  - **Filter / sort / group** toolbar — search (matching the profile chips too, so "stacked"/"cluster" finds the games that use them), client + game-type + status (incl. *Engine stale*) filters, four sort orders, and **group by client** on by default.
  - **Duplicate** (`POST /api/game-maker/duplicate` + `src/lib/server/projectDuplicate.ts`) — copy a game onto a new key in the same or another client, for reskins. Two scopes: `setup` (authoring docs only — fast, art comes later) and `full` (asset folders too, capped at 4000 objects and refused rather than truncated over it). **Two roots are copied, not one**: `<client>/<project>/` AND `editor/<projectKey>/` (components + component-defaults live outside the project prefix; missing them yields scenes referencing prefabs that only exist for the source). Every `.json` body is **re-based** on the way across (project R2 prefix, component root, and the self-naming `projectKey`/`output_prefix` fields, matched by field name so a project key that is also a symbol id or a word in a string is never touched) — a byte copy would leave the duplicate silently reading the *source's* assets. Gated like Create (any `gameMaker` holder) + access to the source; the new project row is rolled back if the copy throws. Verified offline over the real modules (profile rendering for lines/ways/scatter/no-config, plan + rebase fixtures).

**Reskin / template games work today:** background, scenery, HUD, free-spin intro/counter/outro, loading splash, board position/shape/spin-feel, fonts, localized text, and per-instance prefab art are all doc + R2-driven.

## Open items / next
0. **Standing convention — a new optional mechanic ships with its detector.** When the engine gains an optional mechanic or presentation feature, add its row to `FEATURE_DETECTORS` in `apps/launcher-api/src/lib/server/gameProfile.ts` **in the same change**. It is one entry, it needs no page edit, and it is the only thing that keeps the hub's "Using:" list from silently under-reporting what a game does. If your signal isn't in `ProfileContext` yet, add it to the context and to the loader that assembles it — never do IO from inside a detector.
1. **Phase 2 — config from R2: ✅ done, as [Invisible Game Config](game-config.md).** A project with no saved `/config` doc plays its type's compiled template by design. **Residual still-compiled** = a few `constants.ts` feel knobs (`SYMBOL_SIZE`, `SYMBOL_SPINE_FILL`, `REEL_PADDING`, `SPIN_OPTIONS_*`, background ratios, `zIndexes`) with no per-game authoring home; they rarely need one.
2. **Phase 3 — more game-types: resolved as ONE shared runtime, not a bundle per type.** `runtimeFor()` in `publishGame.ts` returns `SHARED_RUNTIME_ID` for every type: the shared bundle (built from `apps/lines`) adapts to the config's `winModel`, and a `_runtime/ways` built from the vanilla `apps/ways` could not consume a runtime bundle at all (Phase D of [game-type-templates.md](../design/game-type-templates.md)). A per-type bundle is worth revisiting only for a type that needs bespoke compiled code — `cluster`'s tumble board is the first candidate.
3. **Phase 4 — behavior tracks (the long pole).** Novel per-event animation is still per-game TypeScript (`bookEventHandlerMap.ts`); the declarative `tracks?: BehaviorTrack[]` format + interpreter + versioned vocabulary is a multi-quarter engine project, own design doc.
4. **Authoring boots still export on the read path.** Players boot a published snapshot (no exporter runs), so what is left is AUTHORING latency (launcher links, `ie_authoring=1`, ~20-26s per cold assemble), not correctness. The 10s `runtimeBundleCache` TTL is shorter than one assemble, so it only collapses concurrent bursts; getting under it needs the exports moved to save/publish (`publishGame.ts` already calls `ensureDeployExports`), after an audit that every authoring tool exports reliably on save. **Do not raise the TTL without a real source fingerprint** — the bundle's inputs span `<client>/<project>/`, `editor/<projectKey>/components/` and `_shared/editor-components/`, and a fingerprint that missed one yields a false HIT. Client limits in `apps/lines/src/editor-scenes.ts`: authoring 150s per attempt / 210s budget, players 45s / 120s.
   - **Where the time goes (2026-09 profiling, #756/#762/#776/#782/#784: 83-97s → ~25.5s).** `art` (~23.6s, dominated by `art:manifests` ~9.1s, already 6-wide via `mapWithConcurrency`) is the ceiling; `symbols` and `flipbooks` run beside it. Measure quiet (60s apart) — back-to-back assembles contend and inflate every phase.
   - **Two lessons that moved nothing when ignored:** a fix counts only on the CRITICAL PATH (`art` and `symbols` run in parallel, so halving `symbols` bought zero), and removing duplicated work that ran CONCURRENTLY saves R2 load and memory, not wall clock. Only sequential work is a latency win.
   - **Concurrency hazards already closed in `editorArtExport.ts`:** stems are assigned in a synchronous planning pass (`plannedStems`) so two sheets can't claim the same `editor-art/<stem>/`; `PageStore.ensure` is single-flighted per source key; `sheets`/`spines` are canonically sorted so the bundle is byte-stable. `scripts/verify-art-export-concurrency.mjs` guards them. A sheet that bails after claiming its stem leaves a harmless `_2` gap.
   - **Reading the breakdown:** `Server-Timing` is emitted only for a request that actually assembled (none for a cache hit or in-flight join): `curl -D headers -o /dev/null "…/api/editor/runtime?project=<p>&k=<readToken>&authoring=1"`, then sort by `dur=`.
5. **Published-snapshot follow-ups (2026-09-29).**
   - **A snapshot freezes DATA, not the engine.** The shared `_runtime/lines` still re-points every online game on each engine merge, so an engine change that needs NEW bundle fields meets older snapshots until they are republished. The engine must keep reading older bundles (every field is already omit-when-empty/parity), and an engine PR that changes the bundle contract must be followed by **Republish all** — the existing "Engine update available" badge is the prompt. Rolling back to an older snapshot widens the gap.
   - **The launcher home's Games cards (and partner-RGS cards) still open LIVE authoring data** (`ie_authoring=1`), unlike Game Maker's **Play ↗**. Deliberate for now — they are author links — but it is a decision, not an accident; revisit if those cards become player-facing.
   - **Writers outside the launcher's lock:** the Python atlas tool writes `<client>/<project>/deploy/<atlas>/…` directly. Those files are exporter INPUTS, not files `runtime.json` references, so they cannot desync a snapshot — they are only dead bytes copied into each one.
   - **A player tab open across five further publishes** can 404 on lazily-loaded assets once its snapshot is swept. Acceptable at five; raise `RETAINED_SNAPSHOTS` if sessions get long.
   - **Legacy games** (published before snapshots) keep the live-assemble fallback until republished. Which games are still legacy is visible on their Game Maker card (the amber "Published before versioned snapshots" note) and in the `X-IE-Runtime-Source` header of a player `/api/editor/runtime` fetch (`live-fallback`). On 2026-09-29 test1/2/3/6, cloud and the remake were republished within minutes of the release (test6: 26.2s → 0.53s); test4 and test5 were still legacy. **Republish all** freezes the rest, after which the fallback only covers a missing/corrupt `runtime.json`.
   - **Engine pinning is recorded, deliberately not enforced** (#849): `SnapshotMeta.engine` names the runtime release a version was published on, but no games.json `runtimeVersion` pin is written — a pinned game would stop receiving auto-releases and engine rollbacks. Data rollback and engine rollback stay separate levers.

## ⏳ Live-verify
- Published snapshots on a second launcher replica or across a Railway deploy overlap (two processes): the pointer is CAS-written and the sweep leaves unreferenced folders younger than 1h alone, but the per-project deploy lock is in-process only. Verified offline (`check:published-runtime`), not with two live processes.
- Bulk republish against real projects: the progress panel (bar, per-game states), a desktop-built game reported as *skipped*, **Stop after this game**, re-attach after navigating away, and the stale badges clearing when the run finishes. The walk's semantics (order, skip-vs-fail, cancel, timing) are covered offline over the real `publishAllRunner` module.
- On-screen Pixi render / boot-order timing for the runtime boot is owner-confirm only (headless gate PASSED).
- Publish pin fix: rebuild a non-active project → selection lands on it (owner verify owed).
