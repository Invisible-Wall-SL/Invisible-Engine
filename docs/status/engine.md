- **Signal-subscription re-entrancy loop (fixed)** — a slammed free-spin **outro** could crash the reactive cycle with `effect_update_depth_exceeded` (Svelte 5), which aborts the update pass so downstream nodes freeze and the screen reads as broken. Root cause: `ComponentInstance.svelte`'s signal-subscription `$effect` subscribes to registered signal sources, and a source may EMIT SYNCHRONOUSLY on subscribe — the seed-on-subscribe latch (`freeSpinOutroCountUpComplete` fires `run()` immediately when `freeSpinOutroState.countUpComplete` is already true, the fix for the instant-count-up race). That emission runs the callback INSIDE the subscription effect, and `fireComponentSignal` READS + WRITES `firedSignals[key]` → the read leaks as a dependency, the write re-invalidates the effect, it re-subscribes/re-seeds/re-writes → infinite loop. It only surfaced on a SLAM, where the outro count-up completes in the SAME tick the outro-visual instance (tap armed on `freeSpinOutroCountUpComplete`) mounts + subscribes, so the latch is already set. Fix: wrap the subscription SETUP in `untrack(...)` (the effect has no legitimate reactive deps — `signalToTargets`/`gateSignals`/the registry are init-stable — so it should subscribe exactly once; mirrors `LayoutScene`'s tap-portal guard). Untrack suppresses dependency TRACKING, never the writes/notifications, so later emissions still fire cues + update `hiddenUntilSignal`/`tapArmed`. Reproduced deterministically headless (forced trigger + retrigger via the book mock, then Space-spam to slam the outro) and confirmed gone across 600+ slams / 24 free-spin rounds. The R2 keys live in GitHub Actions secrets, so a release needs no keys on a dev machine. **Gated and verified (2026-09-28):** before anything is stamped or uploaded it runs `check:undefined-names` (now `.ts` AND `.svelte`), `check:engine-game`, `check:rgs` and the build; after the upload it POSTs `/refresh` and polls a game on the runtime until the served `index.html` names the `bundle.<hash>.js` it just built, re-POSTing `/refresh` with backoff, and goes RED if that never happens within 15 min (`apps/launcher-api/scripts/verify-runtime-live.mjs`). See "Rollback" below. Game Maker's Publish CANNOT do it: `publishGame` only points a game's manifest at the prebuilt `_runtime/<id>` and "never rebuilds". Standalone games (desktop-launcher builds) get it from the `engine` submodule, which the launcher's publish advances to `origin/main` before every build — and since 2026-09-17 that covers the **whole** engine, `apps/lines/src` included, because a game repo no longer carries application source at all (2026-09-17 entry in [engine-history](engine-history.md)). - **Rollback — a pointer flip, no rebuild (versioned releases, 2026-09-29).** Each release lands in its own immutable `test_server/_runtime/lines@<version>/` and goes live by ONE write of `_runtime/lines/current.json`; the test server resolves that pointer on every hydrate. Layout, canary and retention: "Runtime releases" in [games-deploy](../design/games-deploy.md#runtime-releases-the-online-games-engine).
  1. **Take the bad release back:** GitHub → Actions → **Runtime rollback** → Run workflow → action `rollback`, version empty (= the next older release that was ever live) or a version / commit; or `gh workflow run runtime-rollback.yml -f action=rollback`. The run flips the pointer, POSTs `/refresh` and stays running until a game serves the chosen release (`bundle.<hash>.js` + the `X-Runtime-Release` header), so green = live. `action=list` shows what can be picked.
  2. **Then fix `main`:** `git revert <bad-sha>` → PR → merge. `main` still holds the bad commit after a rollback, and the next engine merge would release it again. Roll forward with action `promote` (empty = newest release) once a good release exists.
  3. **Confirm by hand if needed:** `curl -sI "https://games.invisiblewall.org/bookofborutremake/index.html?cb=$RANDOM" | grep -i x-runtime-release` names the release; `https://games.invisiblewall.org/healthz` lists the pointer version per runtime and every pinned game. Never fetch the bare `_app/immutable/bundle.<hash>.js` URL to check — an early 404 carries no cache headers and can stick in a browser or proxy cache.
  - A release that fails after its `building` stamp (gates, build, upload, served check) now puts the stamp back to the live release and records `lastFailure`; the launcher reads "Engine deployed · <commit> · last release failed" instead of "Releasing engine…" for 30 min.
  - **Still open:** `Lint` is still not a required check on PRs (branch protection needs a paid plan), so the release gates are the backstop, not the first line. An auto-release on merge always promotes; the canary path (release unpromoted → pin a test game → promote) is manual.

- **Delivery profile — a build hosted by someone else (Phase 1 of [delivery-builds](../design/delivery-builds.md), 2026-09-14)** — `packages/delivery-profile` carries the two facts a build cannot know about itself when a partner/client/aggregator serves it from their own domain: which RGS it talks to, and how their page hands over a session. Resolution is later-wins: `DEFAULT_DELIVERY_PROFILE` (restates the pre-profile behaviour) ← the profile baked by `PUBLIC_DELIVERY_PROFILE` (injected as `__IE_DELIVERY_PROFILE__` by the SHARED `packages/config-vite`, so a game repo with the engine as a submodule inherits it) ← `config.json` served next to `index.html` ← URL params, and only while `rgs.allowUrlOverride`. Read by `stateUrlDerived.rgsUrl()`/`sessionID()` and by the Play4Fun transport (endpoint path + credentials mode); **awaited in `components-shared/Authenticate.svelte`**, not in an app's `+layout.ts`, because every app mounts `<Authenticate>` while only `apps/lines` has a layout `load` — a game repo scaffolded by `new-game.mjs` has none, so a delivery cut from one would have baked a profile whose `config.json` was never applied. **Inert without a baked profile** — no fetch, no log, no behaviour change — which is the parity guarantee for every game already live. Two decisions carry the weight: `rgs.withCredentials: false` for a delivery, because the `sid` is the credential and credentialed CORS forbids the wildcard origin that is the only answer scaling to an open-ended set of hosting domains; and `session.required`, which turns a missing token into an `ERR_NO_SESSION` modal instead of the minted `demo-<uuid>` — a phantom wallet taking real spins is worse than a game that plainly refuses to start. A broken profile fails the BUILD (`config-vite` shape-checks the baked JSON and throws) — the opposite posture from the runtime merge, which degrades, because nothing is running yet and a profile that merged down to internal defaults would ship a delivery pointing at no RGS. `config.json` may **repoint the build but not re-police it**: host/endpoint/session-param are overridable, the three security fields are bake-only. Verified: an offline fixture of 8 claims (`profile.fixture.ts`), a typo'd profile failing the build with a named field, and — served from a plain static host — a real delivery build resolving baked ← `config.json`, refusing a re-policing override, ignoring `?rgs_url=`, refusing to boot with no token (zero RGS calls), then authenticating on `?sid=`; plus the no-profile build re-checked in the same harness with **no `[delivery]` output, no `config.json` fetch** and `?sessionID=`/`?rgs_url=` behaving exactly as before.

- 2026-09-21 — **paint order on the board stopped being a function of when a cell happened to mount.** Two owner-reported symptoms on the live `test6` (stepped `5×[3,4,4,4,4]`, perspective authored, cascading) were ONE defect: `pixi-svelte`'s `addToParent` does `addChild` inside `onMount` and nothing ever re-derives the order, so a component's markup order fixes the stacking only of the children that mount TOGETHER — anything that unmounts and remounts is appended to the END of its parent and paints over every sibling until the parent is rebuilt. **Its signature is worth memorising: *right when it first appears, wrong after the first spin, right again after a reset or hide/unhide.*** It bit at two scales. (a) **Board cells** — a cascade splices its refills ABOVE the survivors as NEW cells (`combineTumbleReel`), so the refilled top rows drew over the board; the perspective branch in `BoardBase` exists precisely to buy back-to-front painting and survived only until the first cascade step. Proven by reading the board container's real child order off `globalThis.__PIXI_APP__` on the live game — the last five children were all top-row cells, and a second capture a few spins later drifted differently, because the stacking encodes arrival history rather than board position. (b) **Layers inside a cell** — `layers` resolve per STATE, so a spin binding different layers unmounted them and an authored shadow came back in FRONT of its character. **Fixed** with a seat-derived `zIndex` per cell (`apps/lines/src/game/paintOrder.ts` — extracted from the component so the rule is testable without a renderer) in a band `(0, 0.5]` strictly between the ground layers at 0 (`BoardMask`, `BoardTiles`) and `BookVfx`'s foreground at +1; `StackedPicture` states its own `0.75` because it had been riding mount order above the symbols. Inside a cell, one **unconditional container per band** (the device the base art already used — "UNCONDITIONAL on purpose") plus a `zIndex` within a band, because a ripple and a shadow are both *behind* layers and a wrapper alone would still let them swap. Sorting is safe on a band container because this component owns it outright, where a cell's own parent varies by mount site. **The rank arithmetic has no upper bound on purpose, and the first version got this wrong:** a cell's row is its index in `reelState.symbols`, which mid-roll becomes `[...targetSymbols, ...paddingSymbols, ...prevSymbols]` with the padding ACCUMULATING per reel, so a plain 5×3 board runs columns 16 deep on reel 0 and 40 on reel 4 — a `rows*2+2` budget was blown on every spin and columns spilled into each other's range, ordering every board WRONG, including flat non-cascading ones. `1 - 1/(row+3)` squashes any index into `[0.5, 1)`, so `reelIndex + depthOf(row)` is column-major for any strip length. New `scripts/verify-board-paint-order.mjs` (20) drives **real PixiJS Containers** through the mount sequence a spin performs and **reproduces both bugs** on the old shape before asserting the fix; `verify-symbol-seat.mjs` (274,644) still passes and svelte-check is unchanged at 193/61. Known bound, stated in code: under perspective a reel that is actually ROLLING ranks by strip index and sorts above the settled columns (perspective boards are not meant to roll — that is `swapInPlace`). **Shipped and VERIFIED LIVE** (#759, `b3170d82`) — owner-confirmed on `test6` after the automatic runtime release that the merge triggered. One caveat for anyone re-running the child-order probe: on a board that is stepped AND perspective the correct order is row-major by SEAT ROW, so a probe comparing against an `(x, y)` sort will report `DRIFTED` while the board is right.
