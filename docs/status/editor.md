# Invisible Scene Editor — status

> Design: [docs/design/invisible-editor.md](../design/invisible-editor.md) · Guide: [docs/tools/invisible-editor.md](../tools/invisible-editor.md) · Agent: `.claude/agents/invisible-components.md` (component-focused; not a registered spawnable agent)
>
> Companion tool: [Component Editor status](./component-editor.md) — this editor **places** component instances; that tool **authors** the `ComponentDef`s.

**One-line state:** Built — the full 10-step build plan + Templates/Import (§7) are on `main`, registered (`editor` tool) and documented; ⏳ **many editor render paths are code-only / not browser-verified**, and new/reordered non-`background` screens still don't drive the shipped game generically for the reference games.

## Current state
Launcher-native, full-page WebGL/canvas layout editor at `/editor` (auth + `editor`-tool gated; SSR off, `load` runs server-side). Project-centric: loads the active project's `scenes.json`, asset library (atlases/spines/sheets/effects), components, and its game-type template. Layout is written to R2 at `editor/<client>/<project>/scenes.json` on a debounced autosave; the engine fetches it at boot (`GET /api/editor/doc`, `EDITOR_DOC_SECRET`-gated) and renders it via `<LayoutScene>`, falling back to the checked-in `editor-scenes.ts` fixture.

Shipped capabilities on `main`:
- **Screens** — game + HUD screen lists (reorder within group, rename, hide, duplicate, delete); per-screen coordinate **space** (`game` / `standard` / `canvas` / `background` cover-fit); per-screen **"Always on top"** tick (`Scene.alwaysOnTop` — opt OUT of list layering and pin to the fixed top band; `TOP` badge on the row); scaffold from a **game kind** (§21), **import composed reference** (§7.2), add-missing-screens, "Save as new game kind".
- **Canvas** — real-texture rendering (spine previews as a live skeleton; FX render **live particles** as an overlay following pan/zoom), zoom/pan/Fit, multi-select, transform handles (move/scale/rotate), snap-to-node guides, undo/redo, copy/cut/paste/duplicate.
- **Library placement** — Text / Rect / Reel elements, atlas pages + manifest regions, spines (+ `_shared/`, upload), sheet regions, and **Invisible FX** effects (place free or attach-to-rig; particle atlas ships automatically).
- **Per-region drag/thumbnail/overlay** (§B18) — each sheet/atlas-manifest row expands to individually-draggable region thumbnails (`RegionThumb.svelte`); selected node gets a floating item toolbar (`EditorItemOverlay.svelte`) with delete/lock/anchor/z-order.
- **Properties** — transform/tint/text/spine anim/background cover-fit + slot fill; node actions (Convert to reel grid / parametric button / Edit as component). Reel-grid **symbol size (× cell)** (`reelGrid.symbolSizeRatios`) is authored here and bakes on the normal scene bake.
- **Device layouts** — `desktop · tablet · landscape · portrait` per-layoutType overrides; per-layoutType **Canvas Size** (the MAIN box), seeded from the game type's reference with a "Match game box" warning/fix.
- **Flow owns visibility** (standing rule, 2026-07-03) — the per-screen and per-instance "Shows during" gates were removed; a screen/instance's visibility now comes from Invisible Flow, not a Scene-Editor field.
- **Generic doc-driven scene mounting** (§20.1, PR #67) — an author's new Scene Editor screen ships without hardcoding it in `Game.svelte` (`engine-layout/genericMountScenes.ts` + Flow Phase 4 `activeScreenTakeover`), parity-gated.
- **Templates** — a template-authoring mode (tag nodes with `slotId`, choose game type, save `editor/templates/<gameType>.json`) + slot/asset-issue warnings on save (§7).
- **Pipeline** — layout-doc bake + **editor-art export** (`deploy/editor-art/`, per-sheet namespaced) travel the export→deploy→bake→pull→register chain.

## Open items / next
1. **New / reordered non-`background` screens don't yet drive the shipped reference games.** They mount scenes by hardcoded id in fixed code order, so a brand-new empty/HUD screen or a reorder changes the **editor preview** but not the built game (only `background`-space scenes mount generically today; Flow Phase 4 covers exclusive-screen takeover). Wiring the runtime to render doc scenes generically by doc order is the next engine step.
2. **Reference layouts for `ways` / `cluster` / `scatter`** — only `lines` / `bookOf` have rich reference scene sets; other kinds scaffold from a bare skeleton.
3. **HUD parity gaps** — the corner logo/game-name containers still ignore `scale` in-game (rotation now ships), so scaling those two corner texts in the editor won't ship yet.
4. **Animated / book-event content stays coded** — symbols, win-line draws, count-ups mount via the engine `mount`/`bind` escape hatch; the editor only places their anchor and has no in-editor book-event playback (verify animated behaviour in the live game).

## Blocked (owner / external)
- **`EDITOR_DOC_SECRET`** must be set on the launcher for the live-doc fetch to serve; unset ⇒ endpoint refuses and games fall back to `editor-scenes.ts`.
- **Engine submodule bump required for shipped games** — Book of Borut and other shipped games vendor the engine as a submodule, so editor/engine parity fixes only reach them after the submodule is bumped and the game rebuilt (owner-owned).
- **Live-verify** — interactive feel (undo/redo, copy/paste, multi-select) and several render paths build clean and type-check, but the auth-gated canvas makes automated interaction testing hard; owner confirms live.

## Recent changes
- 2026-07-17 — **An unset boolean param drew unchecked while the game read `true`** (found while diagnosing the book-reveal panel: "symbol follows bone rotation" showed OFF though its default is `true`). The instance-params panel read `checked={Boolean(node.params?.[p.key])}` — the RAW value, ignoring the def default — while every other kind in that panel falls back to it (selects render `(default: x)`, texts placeholder it) and the runtime resolves `booleanParam(k) ?? <prop default>`. So for any default-TRUE param the panel stated **the opposite of what the game did**, and an author "turning it on" was a no-op against a value already on. Now unset ⇒ show `p.default === true`; an explicit `false` still reads as unchecked, so ticking/unticking keeps writing explicit values. Verified with a fixture over the real def across `{}` / `{followRotation:false}` / `{followRotation:true}`: the old expression mismatched the runtime on 4 combos (both `followRotation`/`followScale` when unset), the new one matches on all. Only `freeSpinIntroSymbolReveal` ships default-true booleans today, so no other panel changes. Editor-only; no runtime publish.
- 2026-07-17 — **Dropdowns instead of free-text for values the tools already know** (owner-reported: "why do I have to type it? sounds counter productive since everything is already authored"). Three findings behind one complaint, on the `freeSpinIntroSymbolReveal` panel. (a) **`symbolBone` rendered as a text box** — the `spineBone` kind IS a dropdown and its render arm always handled it, but `EditorProperties`'s `neededSpineKeys` prefetch listed only `spineAnimation`/`spineSlot`, so a bone param never fetched manifest meta and silently fell through to the free-text `{:else}` whenever the canvas hadn't published LIVE meta (marker-only preview, or a rig that never settles) — the exact gap the manifest fallback exists to close. Added `spineBone` to the prefetch. (b) **`symbolState` was declared `kind:'string'`** so free text was all the panel could render — for a CLOSED set the Symbols tool next door renders as fixed grid columns. New `symbolState` param kind + a `<select>` of `SYMBOL_STATES` labelled with the same `STATE_LABELS` the grid uses (so a state reads identically in both tools), keeping the spine dropdowns' `(custom)` passthrough so an existing typed value never silently vanishes. (c) **The real one — `componentStorage`'s `PARAM_KINDS` allowlist was missing `spineBone`**, so saving a forked copy of the def STRIPPED `symbolBone` outright (latent author-data loss). Its own comment documents this exact bug happening once before with `spine`/`spineAnimation`/`spineSlot`; nobody extended it when `spineBone` shipped. Fixed structurally rather than by hand: `COMPONENT_PARAM_KINDS` is now a VALUE in `engine-layout/types.ts` that the `kind` union derives from, and the validator imports it — a copy can't drift if there's nothing to copy. A `Record`-keyed compile-time guard was tried FIRST and rejected on evidence: **the launcher has no type-check at all** (`build` is a bare `vite build`, no `svelte-check` dep), proven by deleting a key and watching the build still pass — so a compile-time-only guard would not have caught (a) or (c) either. Same DRY pass collapsed `SYMBOL_STATES`, which existed in THREE hand-synced copies (`apps/lines/game/types.ts`, `server/symbolsStorage.ts`, the browser-side `symbols.client.ts`) — all now re-export `engine-layout/symbolStates.ts`, the one home both the launcher and the games can import. Verified offline with an esbuild+Node fixture over the real modules (the `dist` is unrunnable directly — extensionless imports, `gotcha_symbols_publish_silent_double_fail`): all 11 def params now KEPT where the old allowlist dropped `symbolBone`, every state labelled; `launcher-api` + `lines` build clean. **No runtime publish needed** — nothing at runtime branches on a param KIND (the runtime reads param VALUES, and all three affected kinds stay plain strings); the kinds are editor input hints, so this ships with the launcher deploy alone. ⏳ Live-verify pending: the panel needs an author to open a `freeSpinIntroSymbolReveal` instance against a real rig.
- 2026-07-16 — **"Behind the reels" tick — an overlay screen can finally mount UNDER the board** (owner-reported: "background_left/background_right are overlay screens, placed under the reel in the Scene Editor, but they render on top in the game"). This was the REAL bug behind the layering report (the takeover fix below is a separate, latent one — `bookofborutremake` is v2-driven, so its takeover never mounts). The whole list-ordered band starts at `LAYER_BAND_BASE = 100` and the reel board is engine-owned at the **implicit z 0**, so EVERY list-ordered screen sat above the reels: no list position could express "behind the board", and the `basegame` row was inert for layering. Dragging an overlay above it looked right and did nothing. Fix: sparse `Scene.behindReels?: boolean` + a new `LAYER_BAND_BEHIND = -500` band (doc-index-ordered, so under-reel screens keep their list order). Making room meant re-banding the backdrop: authored `space:'background'` scenes -10 → `LAYER_BAND_BACKGROUND = -1000`, and the coded `<Background>` (which emitted its own `-3..-1` children straight into the root) is now WRAPPED at `LAYER_BAND_BACKGROUND_CODED = -900` — relative order unchanged, so it's parity for every game, but it opens a real gap between the backdrop and the board. Editor: a "Behind the reels" tick in Properties (mutually exclusive with "Always on top" — ticking one clears the other) + an `UNDER` badge on the row; whitelisted in `normalizeScene`. Full map, low→high: authored bg (-1000) → coded bg (-900) → behind-reels (-500+i) → **board (0)** → list band (100+i) → pinned (9000+i) → engine gates (10000). Verified against the live doc: Background 2 / BackgroundRight land at -499/-498 — under the board, in front of the backdrop, list order preserved. ⏳ Needs a runtime publish.
- 2026-07-16 — **Custom kinds + game-type templates are conflict-guarded too** (Phase 1 cont.).
  Both live on GLOBAL `_shared/` keys, so no project lease can ever cover them. A **kind's id is
  derived from the author's chosen NAME**, so two authors picking the same name silently replaced
  each other's kind — now `ifNoneMatch` → 409 → "already exists, overwrite?" (the Font Maker's
  id-collision contract, but enforced by R2 rather than an in-request check that a race defeats,
  cf. [[bug_font_maker_id_collision]]). Templates are re-saved rather than created, so they CAS on
  an ETag; `/api/editor/template` GET now returns `{ template, etag }`, and switching game type
  re-adopts the new object's etag — a save must guard the object it's about to write, not the one
  the page happened to load with.
- 2026-07-16 — **Autosave no longer clobbers a concurrent author** (Phase 1 of
  [multi-user-concurrency](../design/multi-user-concurrency.md)). The editor serialized the WHOLE
  doc and PUT it unconditionally every 1.2 s, so of two people on a project the later writer erased
  *everything* the other did — not just the conflicting nodes. `saveDoc` stamped `updatedAt` and
  never read it back. Now the loader returns the doc's ETag, the client sends it on every save, and
  a stale one answers **409** instead of overwriting: local work is kept, `dirty` stays true,
  autosave PAUSES (else it would 409 every 1.2 s), and the save pill offers **Reload theirs** /
  **Overwrite with mine** — losing someone's edits is now a decision, not an accident. The three
  flush-before-navigate hops (component editor) refuse to leave when the flush didn't land, instead
  of silently discarding the doc. **VERIFIED live** (owner, 2026-07-16): normal autosave unaffected,
  and a two-tab test on one project raises the conflict banner with the loser's edits intact.
  (Repeated autosaves passing is the stronger signal of the two — each save rotates the ETag, so a
  client that failed to re-adopt it would 409 on its *second* save, not its first.)
- 2026-07-16 — **A flow-active screen now layers from the Screens list + an "Always on top" tick** (owner-reported: "new authored screens moved in the screen layering still render on top in the game"). Every screen path read its z from the doc `scenes[]` index (`docLayerZIndex` = `LAYER_BAND_BASE + index`) — **except** the flow's ACTIVE-screen takeover, which `Game.svelte` pinned at the hard-coded `LAYER_BAND_TAKEOVER` (9000) constant. So a **persistent** flow-active screen was stuck above everything with no way to re-layer it and no clue why: on `bookofborutremake` the author's "Progress Bar" (`s_q9iw9aqf`) is the v1 flow's `initial: true` screen ⇒ takeover ⇒ z=9000, while its list position said z=103. Diagnosed from the LIVE doc + the live Pixi stage (`__PIXI_APP__.stage` children read `z=105`/`106` = correct `100+index`, `sortableChildren:true` — proving the editor, the save path and the z math were all fine, and only the takeover bypassed them). **Fix:** new sparse `Scene.alwaysOnTop?: boolean` + a single resolver `sceneLayerZIndex(scenes, id)` (`layerOrder.ts`) = ticked ⇒ `LAYER_BAND_TAKEOVER`, else `docLayerZIndex`, else `undefined`; EVERY mount path now uses it (takeover — now `$derived`, not a const — plus `extraScenes`, `authoredHud`, hud/overlays/specialBook, and the flow-v2 container re-stamp), so one screen has ONE z regardless of which path mounts it. Exposed in the editor as an **"Always on top"** checkbox in a screen's Properties (with a live "layer N of M — set by the Screens list" readout) and a **`TOP`** badge on the Screens-list row, so the pin is visible instead of hidden in code. Whitelisted in `normalizeScene` (else silently dropped on save — the known `gotcha_scene_field_whitelist_normalizescene` class). **PARITY:** no stored doc carries the new field, so `LayoutDoc.version` went 1→2 with an idempotent read-time backfill (`backfillAlwaysOnTop`) that pins the screens the engine used to pin implicitly — the `loading` ROLE + the legacy `freeSpinIntro`/`freeSpinOutro`/`bigWin` ids — because **the boot splash is takeover-mounted, not coded** (`Game.svelte`'s `<LoadingScreen>` is gone), so without it the splash drops to its list position and paints under the HUD. Matching is role-OR-id: real docs carry `role:'basegame'` as noise, so an `!scene.role` guard misses `freeSpinOutro`. An author's OWN screens are deliberately not backfilled (a persistent flow-active screen is exactly what was wrongly pinned); on v2 a missing tick is a real choice, so the backfill never re-pins. Pinned screens resolve to `LAYER_BAND_TAKEOVER + index` (not a flat 9000) so they keep their list order; `hudZIndex`'s `Math.min` now pins the whole chrome if either HUD scene is ticked (it used to swallow the tick). Verified against the live `bookofborutremake` doc (Progress Bar 9000→103; splash 9005 + outro 9008 stay above the HUD at 112). Round-blocking engine gates (`LAYER_BAND_TOP`) are unaffected. ⏳ Needs a runtime publish to reach the live game.
