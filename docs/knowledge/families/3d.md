# 3D — family knowledge

What is always true about 3D games, where their code lives, and what has gone wrong before. Owner
agent: `games-3d` (builds on `arcade-games`). Plan: `docs/design/3d-games.md`; state:
`docs/status/3d.md`.

## What it is and must stay

A 3D game is an **arcade game** (`family: 'arcade'`) whose play field is drawn by three.js. The
simulation is a real 3D body (`engine-mechanics` `motion3d.js`, y up, metres), and `camera.js`
follows it in metres on the ground plane. The 3D view draws it in its own canvas **under** the
transparent Pixi canvas, so the Pixi HUD is on top and takes every pointer it hits; the stage
forwards the rest to the world's picking.

It ships as a **fifth runtime, `arcade3d`**: the same `apps/lines`, built with
`PUBLIC_IE_FAMILIES=arcade PUBLIC_IE_3D=1`. 3D is a view, not a family: `__IE_FAMILIES__` stays
`["slot","arcade"]`, and `PUBLIC_IE_3D=1` without arcade throws.

Must never change: **the four released runtimes (`lines`, `match3`, `arcade`, `card`) are the same
bytes, file for file, whatever 3D work merges.** A 3D-only merge releases nothing to them.

## Invariants

- **The seam is a resolve rule, not a branch.** `config-vite` `familySeams(list, { view3d })`
  resolves `families/arcade` to `families/arcade3d.ts` when `compiled3d()` is on, except from
  `arcade3d.ts` itself, which re-exports the stock seam and overrides `ArcadeStage` with
  `ArcadeStage3D.svelte`. No file the four runtimes compile names the 3D code
  (`packages/config-vite/families.js`; `packages/config-vite/families.fixture.mjs`).
- **three.js is one lazy chunk of `arcade3d` only.** `engine-3d` is reached only through
  `import('engine-3d')` in `ArcadeStage3D.svelte`; the bundle gains the stage component, the chunk
  holds three.js and `engine-3d`. `check-family-runtime.mjs` markers (`isMeshToonMaterial`,
  `ieWorld3d`) must be in `arcade3d` and in no file of the other four.
- **`three` is declared by `packages/engine-3d` alone, at an exact version** (`apps/lines` may not
  add a third-party package: `check:game-app-deps`).
- **Bytes are proven, not argued.** `pnpm check:runtime-bytes` builds every runtime with
  `IE_REPRODUCIBLE=1` and hidden source maps (as the release) and compares every file it ships
  (code with gzip sizes, every other file by hash) with `scripts/runtime-bytes/<id>.json`. On `main`
  it decides from the last push whose run built, never the push's own diff (`--reaches`): a
  cancelled run once hid an engine merge. A 3D PR leaves the four 2D manifests untouched; `arcade3d`'s is
  re-recorded when it means to change it.
- **The manifests are Linux's.** A Windows checkout (`core.autocrlf=true`) builds different bytes
  (CSS +264 B, bundle ~+450 B, `libktx.js`): record them with `--update` on any Linux checkout,
  in any folder (`config-svelte` sets Svelte's `rootDir`; `check:build-paths`), or take the
  `runtime-bytes` CI artifact, never a Windows `--update`.
- **A merge that does not change a runtime does not release it.** The release builds a reproducible
  twin and ends "unchanged" when the live release recorded the same hash (`releases.json`
  `reproducible`). A lockfile change once re-hashed every runtime (`__IE_BUILD__` carried its hash):
  `IE_REPRODUCIBLE` pins `lockfileSha256` (#1707). **`arcade3d` is dispatch-only** (`release:
'dispatch'`, `runtimes.ts`) until a game plays it: a push releases `PUSH_RELEASED_IDS`.
- **The world canvas exists before the Pixi context.** `families/arcade3d.ts` reserves it at import
  (`game/world3dCanvas.ts`, `z-index: -1`, hit-testable), so `measurePageBackdrop` sees a
  non-ancestor under Pixi's canvas and auto-opaque answers "transparent". A world canvas made
  later, or made `pointer-events: none` (which `elementsFromPoint` skips), brings the black world
  back (auto-opaque decides at init; a later `background.alpha = 0` is too late). The Pixi canvas
  sits above the world, so the stage hides every backdrop layer each frame (the coded background
  band and each `space: 'background'` screen); the Scene Editor marks those NOT IN 3D.
- **The 3D canvas has its own pixel ratio and its own quality controller**: `min(device DPR,
cap)` × the rung of `engine-3d` `createQuality3d` (the 2D controller's rules on a 3D ladder). It
  may be below the HUD's, never above it, and never under half the cap; the HUD's controller does
  not move it.
- **What `engine-3d` computes without three.js is in `pure.ts`** (rig, axes, play loop, camera,
  touch, tiers, quality, anim graph, arena) and pinned in Node by the `check:engine-3d*` gates.
- **A `world3d` game joins the `arcade3d` room, everything else the 2D one.** The seam's
  `joinOnlineRoom` (`game/online3d.ts`) decides by the raw config's `arcade.world3d`, never by a
  `game-config` field (it drops the block). The device's side is `engine-3d` `createRoomView3d`:
  its predictor starts from the first state that shows the own player (a 3D player is stepped only
  by an input, so that is its home) at `dt = 1 / tickHz` — a different `dt` corrects every step
  (`check-engine-3d-room.mjs` fails on it).
- **The view reads `{ x, y, z, yaw }` per player** (`online3d.d.ts` `Drawn3d`): metres, y up, `y` the
  feet, `yaw` uint16 (0 looks down −z, anticlockwise from above; glTF faces +z, so a body's model
  is turned π, a socket's is not). Own player: `createPredictor3d(...).drawn(alpha)`; others:
  `createInterpolator3d().at(id, renderStep)` (+ `ANIM3D` bits). The sim is the arcade family's.
- **A 3D room is a separate room on the same rules (Phase 1b)**: `roomSim3d.ts`, never the 2D
  room. A player is stepped **by its inputs** and the death-plane respawn is in the fold, so
  `createPredictor3d` equals the room bit for bit (`check:room-sim-3d`); one `CREDIT_SECONDS` behind
  the room's clock, or dropped, rests (a neutral step, `ack` kept) and never hangs mid-air. Caps on
  every config-sized loop (`createLevel3d`, `cellSize` ≥ 0.25): the room builds it on the server.
  Trig only before quantising (`moveFromStick`) or server-side (bots).
- **Reconcile against the room's whole body, never a rounded place.** The own device is sent its
  player's body to the bit (`Player3D` own-only fields through `VIEW_TAG.own`, `bodyOfWire3d`);
  a float32 place put a corrected body inside a ramp, so it sank and corrected forever. Anything
  the sim compares a top against (spawns, levels) stays as authored — no `Math.fround` on the way
  in. A new body field goes on the wire, in `hashBodies3d` and in the predictor's history together.
- **Ramps walk up to `maxSlope`; steeper is a wall** (default 1 = 45°; CrashArena 0.7). Step-ups
  draw on the body's `climb` (≤ `stepUp`, refilled at `maxSlope` × speed), so stairs climb at a
  ramp's pace whatever the tick rate. A generated level keeps its ramps under its characters'
  `maxSlope`. Change what the step does and `MOTION3D_VERSION` (in every room fingerprint) moves
  with the replay.
- **The room steps by the wall clock** (`stepLedger.ts`; Colyseus' timer alone drops time after a
  five-step stall), **and a device steps every step it waits for**: a frame sends up to
  `CATCH_UP_SECONDS_3D` (= `CREDIT_SECONDS`) of inputs, or an honest body owes steps and is rested.
- **A fingerprint hashes what both sides step** (`RoomState3D.world` = `worldHash3d(sim.world)`): a
  generated room's is the seed's world, never the authored config.
- **Rules moves leave the fold — predict them, don't correct them (Phase 3a).** With Crash rules
  (`crashRules.js`, server only) a dead player is HELD (inputs acked, not stepped; the view passes
  `still`), a fall is a death (`fallRespawns: false`), and a knockback is a push added right after
  the victim's last applied input and announced with that `seq`: the device writes it in with
  `createPredictor3d` `impulse(seq, kick)` when the event comes before a state that covers it; a
  state that already does carries the pushed body exactly, so it is only noted (gate: one
  correction a kick at most). A rest can fall into a death but presses nothing (`applied(…, rest)`);
  `silent` (the carry-stall drop) never counts catch-up steps. Under rules a swing is the rules'
  `attack` event, never the raw button's `attacked`.
- **The 3D room's Flow names are 3D-only code** (`crashFlow.js`, not `onlineFlow.js`): the 2D
  tables are in the `arcade` runtime's bytes. Adding names to `ARCADE_VOCAB` /
  `SERVER_VARIABLE_SOURCES` moves `arcade` too.
- **A 3D bot walks a grid nav graph, server-only (Phase 3 step 5).** `nav3d.js` derives it from the
  level at load (walk / one-way drop / jump / trampoline `bounce` edges); A* costs are whole mm so
  ties are exact and the bot's rng breaks them — keep them integer (`check:bots-3d`). The Crash
  brain is `crashBots3d.js`, not a `behaviours.js` case (in every 2D runtime); it reads the rules
  through a `situation` (`players`, `pieces`, `pit`); `bots.crash.carry` switches carrying.
- **The world follows the game's clock.** `ArcadeStage3D` adds `world.sync({ deltaMs })` to the Pixi
  ticker; the 3D view has no loop of its own, so a paused ticker pauses it.
- **A character is data, shipped as models** (Phase 2). `arcade.world3d.looks` names a `hero`
  model, its clip libraries (`anim` models) and attachments by the export's own fields (`modelId`,
  `modelIds`), so the publish ships what a look names. A body is drawn from
  `index.models[...].tiers[tier] ?? tiers.full` under the asset base's `models/`; until the model and
  every attachment have loaded the capsule stands in. Clips bind by bone name, so every character on
  one skeleton shares one library.
- **The animation graph is the component state machine; the 3D half is in `engine-3d`.** A
  `CharacterAnim3D` doc's `machine` runs on the shared `ComponentStateMachineRunner`; blends, phase
  sync, masks, additive and weight inputs are read only by `pure/animGraph.ts`. Never teach the
  runner or the 2D normaliser a 3D field (`check:engine-3d-anim`). three averages override weights,
  so layers are per-region sub-clips whose weights sum to 1 on every bone.
- **Replicate gameplay, never animation.** Inputs come from the drawn body (velocity from drawn
  positions, `grounded` from the step or the `ANIM3D` bit); a one-shot the motion cannot show (the
  attack) is a room event, predicted on the presser's device. Nothing about clips, times or weights
  goes on the wire.
- **Big wasm stays out of the chunk.** `config-vite`'s `assetsInlineLimit` inlines every asset
  except the named transcoders (`libktx`, three's `basis_transcoder`): a new wasm dependency of
  `engine-3d` must be added to that list or it lands base64 in the 3D chunk (the Basis transcoder
  did: a 1.5 MB chunk).
- **What every runtime compiles is off limits.** A 3D switch in `game-config`, `engine-layout`,
  `pixi-svelte` or `Game.svelte` changes all four runtimes' bytes; keep it in `engine-3d` or the
  seam, or re-record the four manifests on purpose and say so in the PR.
- **The 3D camera is the director's, beside 2D `camera.js`, never in it** (`engine-3d`
  `src/pure/camera`): rigs as data, the highest-priority active rig on screen, every switch
  blended from the pose ON SCREEN (an interrupted blend must not restart from the old start).
  It is local: it never steps with the sim, only the facing leaves the device. Its shake draws
  from `<seed>:camera` and is a function of seed and time, not of frame cuts. Its collision reads
  the level's colliders through its own collider (`createCameraCollider3d`), never the sim's
  `Level3d` (whose query stamps the step uses). `check:engine-3d-camera` pins all of it.
- **The 3D brawler is first person** (owner, 2026-11-18): `firstPerson` is the default rig; the
  other rigs serve spectating, intros, round ends and debugging; a death detaches to the `ghost`
  rig. First-person collision protects the near plane (a small sweep from the body's axis), it
  does not pull in. Its pitch is the input's aim pitch. The own body is hidden from the camera on a
  render layer the sun's shadow still sees, and the viewmodel draws in its own depth-cleared pass.
- **A camera FOV is vertical: a portrait screen needs the lens** (`CameraLens3d`, `lensFov`). The
  director holds the FOV across below `lens.minAspect`, after the blend, so the pose a switch
  starts from stays the rig's own; never fit a FOV in a rig or feed a fitted one back in.
- **The stick maps through the heading on screen** (`CameraView3d.yaw`, blended), never a rig's
  authored yaw: a switch or an orbit must not change what "forward" means.
- **The 3D camera's Flow words live in the seam** (`apps/lines/src/game/camera3dFlow.ts`), as the
  arcade vocabulary with the 2D world camera's words swapped out; `engine-flow-v2`'s shared
  vocabulary (in every runtime) is not touched.
- **Camera moves are camera NLA tracks in Blender** (`tools/blender/ie_camera_move.py`), one GLB
  per arena, FOV constant per move; the game samples each clip's own tracks.

## Known failure modes

The 3D `models` asset class (upload, optimiser, derive worker, export) keeps its own lessons in
[`lessons/models.md`](../lessons/models.md).

- **A double-sided ramp striped with shadow acne** (Phase 1a): a wedge drawn with arbitrary
  winding needed `DoubleSide`, which casts back faces into the shadow map. Its faces are wound
  outward instead, so it renders and casts like a box.
- **Blender exported no camera animation** (Phase 2): the glTF exporter's `ACTIONS` mode writes
  nothing for a camera object in Blender 5.2. Each move is an NLA track (`NLA_TRACKS`). Guard:
  `ie_camera_move.py` exits 1 on a file with no moves; the gate reads the fixture.
- **A second camera move started where the first ended** (Phase 2): one `AnimationMixer` per
  clip on the same node — a mixer writes a value only when it differs from the last it wrote
  (its cached original), so `roundEnd`'s first position was skipped. Moves sample the tracks'
  interpolants instead. Guard: the gate's "each clip samples its own track".
- **A phone could not move** (review A N1): only the keys moved the player. Touch controls feed
  the same path (`mergeSticks3d`). Their first build lost every drag: the canvas's
  `touch-action: auto` made the browser take a thumb's first move as a page pan and cancel the
  pointer, so the controls set `none` while mounted. Guard: `check:engine-3d-touch` and a
  touch-emulated playtest (CDP `Input.dispatchTouchEvent`, not mouse events).

## How to test

`pnpm check:runtime-bytes` (CI: `runtime-bytes`), `pnpm check:family-runtimes`, the
`check:engine-3d*` gates, `check:arcade-3d`, `check:room-sim-3d`, `check:crash-rules`,
`check:bots-3d`, `check:arena-3d`, `check:three-owner`. Playtests on an `arcade3d` build (headless
shell, muted; system Chrome stalls on the loading screen): `arcade3d-play.mjs` (`--models <deploy>`
from `ie_test_character.py` + `export-models-local.ts`, `--first-person`, `--online`, `--serve` to
play by hand), `arcade3d-camera.mjs`, `arena3d-play.mjs`.
